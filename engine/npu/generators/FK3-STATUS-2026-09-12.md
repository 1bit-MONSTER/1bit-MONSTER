## Chunked-MHA >2-chunk bug — root-cause progress (dsh agent, 2026-09-12 late)

**Reproduced with a clean from-scratch rebuild** (build_mha_chunked.sh), matching
the previous agent's numbers exactly: C=2 N=128 → 956/2048 byte-exact;
C=4 N=128 → 1/2048, max_delta 33878. So the toolchain/build is faithful.

**Diagnostics (npu-build/benches/):**
- The raw-bf16 "byte-exact" metric is misleading. Real error: C=1 mean_abs≈5e-5,
  C=2 ≈2e-5 (row 0), **C=4 mean_abs=0.0031 on outputs ~0.005 (~30-60 % rel)**,
  uniform across all 16 rows. A host float32 simulation of the *exact* online
  algorithm vs full softmax differs by only 4e-6, so the 0.003 is a real bug,
  ~750× above the numerical floor.
- **Decisive probe (probe_uniform.cpp):** set q=0 ⇒ all scores 0 ⇒ softmax is
  exactly uniform ⇒ out must equal mean(V) over all N*C keys.
  - C=1: worst_abs 4.8e-5 ✅  C=2: worst_abs 3.0e-5 ✅
  - **C=4: worst_abs 9.2e-3, 78/128 elements bad; closest to the mean of the
    FIRST HALF of the keys (half01 mean_abs 0.0026).**
  So the softmax math is exonerated: the **V data path loses/corrupts chunks 2–3**
  once the cascade wraps past the depth-2 fifos.
- Execution-order models (model_mhac4.cpp) permuting which score/V chunk each
  loop step sees do NOT fit better than identity, so it is not a simple chunk
  permutation — the last two V DMAs land stale/partial.
- The lowered MLIR is structurally correct: a real `cf.br` loop with modulo-2
  buffer selection and correct shim DMA offsets (V offsets 0/16384/32768/49152,
  all 4 tasks present; QK offsets likewise). The failure is a runtime
  synchronisation/relay issue between the shim/mem-tile DMA and the core for
  iterations ≥ 2 (i.e. **trip count > fifo depth**).
- Depth must be ≥ trip count in this mlir-aie lowering: depth 1 broke C=2
  (`fa493861a` fixed it with depth 2); depth 2 works C=2, breaks C=4; depth 4
  for C=4/N=64 does **not link** (AT buffers 1–3 unallocated — pv_c memory full:
  V 16K + AT 4×8K + E 4×2K + stack 8K = 64K exactly).

**Consequence:** `depth == C` does not scale to @1k (C=8/16 ⇒ buffers >> 64 KB
per core). A fix needs either the mlir-aie objectfifo lowering/relay bug fixed,
or a restructure that never reuses a cascade buffer more than its depth
(e.g. fuse combine into the PV core to drop AT, shrink N, or an explicit
double-buffered handshake the transform cannot reorder).

**Working configurations right now:** C=1 and C=2 N=128 are numerically exact;
the fk-3 fused-layer xclbins (build_fk3.sh) build cleanly and are the viable
path for ≤256-key prefill while the >2-chunk cascade is unresolved.

## ✅ ROOT CAUSE + FIX — chunked MHA >2-chunk bug (RESOLVED, dsh agent)

**Root cause:** `n1_mha_chunked.py`'s `pv_body` called `matmul_pv(e, v, at)` **without
zeroing `at` first**. `mm.cc`'s `matmul_bf16_f32` *accumulates* into C. With the
depth-2 AT ping-pong, chunks 0/1 write AT_buff_0/1 and chunks 2/3 **add on top of
them** instead of replacing them. Measured proof: with q=0 (uniform softmax, so
every chunk must contribute exactly 1/4) the effective per-chunk weights came out
**[2, 2, 1, 1]** — a near-perfect least-squares fit (residual 5e-5) — exactly
predicting `coeffs = Σ alpha products` with AT_buff_0 = AT0+AT2, AT_buff_1 = AT1+AT3.
That is also why C=1/C=2 passed: with C ≤ depth no AT buffer is ever reused.

**Fix (2 lines + a defensive reset):**
1. `n1_mha_chunked.py`: declare `zero_pv = external_func("zero_f32", inputs=[AT_ty],
   link_with="mm_bf16_f32.o")` (mm.cc emits `zero_f32` under `-Dbf16_f32_ONLY`) and
   call `zero_pv(at)` before `matmul_pv(e, v, at)`.
2. `softmax_online.cc` + `combine_attn.cc`: added `softmax_reset()` /
   `combine_reset()` and call them after the epilogue so a re-invocation on the
   same hw_context starts from a clean m/l/O state (the statics live for the life
   of the xclbin).

**Verified on the NPU (clean rebuild):**
| build | before fix | after fix |
|---|---|---|
| C=4 per-chunk weights (q=0) | 2, 2, 1, 1 | **1, 1, 1, 1 (exact)** |
| C=4 uniform probe worst_abs | 9.2e-3 (78/128 bad) | **2.9e-5 (0/128 bad)** |
| C=4 mean_abs vs online model | 3.09e-3 | **2.51e-4** |
| **C=8 (1024 keys = @1k)** uniform probe | — | **2.8e-5 exact** |

The residual 2.5e-4 vs the host online model is the AIE emulated-double exp2 +
hardware mmul accumulation order (the kernel now matches the *exact* online model
to 2.5e-4, and the online model matches full softmax to 4e-6 on the host); it is
the documented "few-ULP amplified through GEMM" caveat, not a structural bug.

Note: repeated `kr(...)` invocations on the **same** hw_context do not re-execute
(run 2 returns zeros); a fresh `xrt::hw_context` per invocation gives byte-identical
results. Worth knowing for the engine wiring.

**Kernel latency (M=16 queries):** C=2 (256 keys) 15.2 ms, C=4 (512k) 28.6 ms,
C=8 (1024k) 55.7 ms → ~7 ms per 128-key chunk, linear. At M=16 this is not yet a
prefill win; the @1k value needs M≫16 (query tiling) so the K/V stream amortises.

**Files changed (all uncommitted):** `n1_mha_chunked.py` (fix + --v-direct/--vs-depth
experiment flags), `softmax_online.cc`, `combine_attn.cc`, `build_mha_chunked.sh`.
Diagnostics: `~/npu-build/benches/{probe_chunkweights,probe_uniform,model_mhac4,

## ⚠ fk-2 audit (dsh agent, round 2): "fused RMSNorm+QKV CORRECT" is FALSE at n_k>1

Built fk-2 reproducibly for the first time (`build_fk2.sh`, recovered from the
session; the `mm_bf16_16x64x128.o` object had been lost in /tmp). Real 0.6B dims:
M=16, H=1024, N=128, k=64 → n_k=16.

**Measured on the NPU (`~/npu-build/benches/bench_fk2u.cpp`):**
| H (n_k) | exact | within 2 ULP | worst rel |
|---|---|---|---|
| 64 (1) | 1084/2048 | 2048/2048 | 0.0077 (**correct**) |
| 512 (8) | 0/2048 | 107/2048 | 1.6 (broken) |
| 1024 (16) | 0/2048 | 0/2048 | 102 (broken) |

Errors grow monotonically with the number of accumulated K-tiles
(`probe_fk2_accum.cpp`: 1 tile → 1 ULP, 2 → 5, 8 → 85, 16 → 100s).

**Root cause #1 (confirmed):** `mm.cc` compiled `-Dbf16_bf16_ONLY` selects the
combo `X(bfloat16, bf16, bfloat16, bf16, 4, 8, 8)` — the **C operand is bf16**.
`matmul_bf16_bf16` therefore loads C as bf16, accumulates ONE K-tile (64) in f32,
and stores C back as bf16. Accumulating n_k=16 tiles with a bf16 round between
each loses ~8 bits per step. A host simulation of exactly that (round C to bf16
after every 64-wide tile product) reproduces the error signature
(worst_rel 0.30 vs true) — so the mechanism is confirmed, though the on-NPU error
is even larger, which points to a **second, still-unidentified factor** (likely
AN/W tile staleness at n_k=16: `probe_fk2_tiles2.cpp` shows each tile is correct
in isolation with random within-tile weights, so the per-tile data and layouts are
fine, but the full random-W case is worse than pure bf16 accumulation predicts).

**Fix (not yet implemented):** make the K-tile accumulator f32.
- Compile the GEMM object with `-Dbf16_f32_ONLY` (C = `float`, `matmul_bf16_f32`)
  so the n_k calls accumulate in f32, then convert to bf16 once with a small
  kernel before the shim output; or
- add a core-local `static float Cacc[DIM_M*DIM_N]` accumulator kernel
  (the `combine_attn` pattern) + a final store/convert.
Then re-run `bench_fk2u` at H=1024 expecting exact-within-1-2-ULP and no
growth with n_k.

**Consequence for the plan:** fk-2 cannot be wired into the engine until this is
fixed. Note fk-3's PoC GEMMs (`mm_ffn.o`, `mm_oproj.o`, `mm_qk_concat.o`) use the
same bf16-C wrapper, but accumulate their full K in ONE call at PoC dims
(DIM_K=64=H), so the PoC is unaffected — the bug appears as soon as those layers
are K-tiled to real dims. `n1_mha_chunked.py`'s PV uses `matmul_bf16_f32`
(C=float), which is why the chunked-attention fix is sound.

### Round-3: f32 accumulator, take 2 — explicit f32 C buffer (also not working yet)

Switched the generator to an explicit **f32 C fifo** + `matmul_bf16_f32` (the same
path the working chunked-MHA PV uses) and an `acc_zero(float*)` helper, so no

(`sizes=[M//4, N//8, 4, 8], strides=[4*N, 8, N, 1]`) no longer de-microtiles it.

Empirical layout map (`bench_fk2map.cpp`, host index -> reference index):
```
0->0 1->1 2->2 3->3 4->256 5->257 6->258 7->259
8->8 9->9 10->10 11->11 12->264 13->265 14->266 15->267
16->3 17->4 ...            (host[0:4] match ref row0[0:4] exactly)
```
i.e. the first four elements are right, then the order diverges — the f32
accumulator's 4x8 tile is stored in a different register/tile order than the
bf16 one. A naive linear `f32 -> bf16` convert (the first attempt) therefore also
failed.

**The remaining work is a bounded kernel task:** dump the f32 accumulator for one
tile with a known input (A=identity-ish, B=pattern) to read off the exact f32 tile
order, then write `acc_store` to emit bf16 in the layout the shim expects — or
change the C output DMA's sizes/strides to match the native f32 order.

`build_fk2.sh` back to the coherent recipe (rebuild verified). `mm_acc.cc`
(now just `acc_zero(float*)`) is kept for the next attempt. Diagnostics added:

### Round-4: f32 C layout probe — partial decode (still open)

`probe_fk2_layout.cpp` (scratch build `~/npu-build/scratch_fk2f32/`) encoded the row
index via the A row shape (A[r][k]=1 for k<=r ⇒ C[r][c]=8·sqrt(r+1), RMSNorm
removes any per-row scale, so the *shape* is the only row encoding that survives)
and the column index via W (W[k][c]=c+1 ⇒ C=64(c+1)).

Row probe (host index → decoded r), first 24 entries:
```
[0..3] r=0   [4..7] r=2   [8..11] r=0   [12..15] r=2   [16..19] r=0   [20..23] r=2
```
So the host buffer walks rows in a non-monotonic 4-element-group pattern
(0,0,0,0,2,2,2,2,0,0,0,0,2,2,2,2,…), i.e. the f32 accumulator's 4-element groups
do **not** correspond to the bf16 4x8 tile order — consistent with the round-3
`bench_fk2map` result. The column probe did not decode at all (no host value
matched 64(c+1)), which suggests the W/column mapping is also being permuted, or
the f32 C buffer is only partially DMA'd out (the C descriptor was generated for
the shape the generator still declares).

Conclusion: the f32-C output path needs a **raw accumulator dump** (write the f32
C buffer to the host with an identity DMA, no de-microtiling) so the native order
can be read directly, rather than inferred through the existing strided C DMA.
That is the next concrete step. No changes left in the tree from this round
(scratch build only); the committed bf16-C generator and `build_fk2.sh` are
unchanged and verified.

## ✅✅ fk-2 FIXED AND VERIFIED — byte-exact at the real 0.6B hidden size (dsh agent, round 5)

**Two stacked bugs, both fixed:**

1. **bf16 accumulator (numerical).** `mm.cc` compiled `-Dbf16_bf16_ONLY` has a
   *bf16* C operand, so every K-tile call rounded the accumulator to 8 mantissa
   bits (measured: 1 tile → 1 ULP, 16 tiles → 10² ULP).
2. **Runtime-sequence C parameter still bf16 (the one that hid everything).**
   After switching `C_ty` to f32 the generator's `@runtime_sequence` still
   declared its C argument as `np.dtype[bfloat16]`, so the shim DMA moved 4096
   bytes over an 8192-byte buffer. That produced the scrambled "256/2048 exact"
   pattern and earlier the half-zero raw dump. **This is what looked like an
   exotic "f32 tile layout" problem — it was a type mismatch, not a layout
   difference.** The f32 accumulator uses the same 4x8 microtile order as bf16.

**The fix (5 lines in `n1_fused_rmsnorm_qkv.py`):**
```python
C_ty  = np.ndarray[(M, N), np.dtype[np.float32]]          # was bfloat16
mo    = "mm_bf16_f32.o"                                    # mm.cc -Dbf16_f32_ONLY
matmul = external_func("matmul_bf16_f32", [AN_ty, W_ty, C_ty], link_with=mo)
zbf16  = external_func("acc_zero", [C_ty], link_with="mm_acc.o")   # was zero_bf16
# and the @runtime_sequence C parameter: np.float32 (was bfloat16)  <-- the key
```
`build_fk2.sh` compiles `mm_bf16_f32.o` (`-Dbf16_f32_ONLY`) + `mm_acc.o`.
**Interface change: C output is now f32**; consumers convert to bf16.

**Verified on the NPU (repo build, host reference = host RMSNorm → bf16 GEMM):**
| M | H | n_k | result |
|---|---|---|---|
| 16 | 64 | 1 | **2048/2048 byte-exact** |
| 16 | 512 | 8 | **2048/2048 byte-exact** |
| 16 | **1024** | **16** | **2048/2048 byte-exact** |

Previously: H=64 → 1084/2048, H=512 → 0/2048, H=1024 → 0/2048.

**Consequences for the fk path:** the same two fixes apply to every K-tiled GEMM
in fk-3 (`mm_ffn.o`, `mm_oproj.o`, `mm_qk_concat.o`, `qkv_gemm.o`): give them an
f32 C and make sure the runtime-sequence argument type matches. This was the #1
blocker for scaling the fused layer to 0.6B dims.

## Chunked-attention PERFORMANCE characterisation (dsh agent, round 13) — it is sync-bound, not bandwidth-bound

Measurements at C=8 (1024 keys), M=16, HD=128:

| variant | kernel time | correctness |
|---|---|---|
| baseline (sync DMA, mem relay) | **54.3 ms** | exact (worst_abs 2.8e-5) |
| async DMA, 4-chunk window (`--async-dma`) | **5937 ms** | **ZEROS — broken** |
| `--v-direct` (no mem-tile relay for V) | fails to load (`std::runtime_error`) | — |
| `--vs-depth 2` | fails to load | — |

**Async-DMA dead end (do not retry):** the shim supports at most **16
simultaneously active BDs**, so C=8 × 3 tasks cannot all be issued; a 4-chunk
window (12 BDs) compiles but produces zeros and takes 5.9 s. The objectfifo
depth-1/2 lock protocol requires awaiting each DMA before its buffer can be
reused — deferring awaits stalls the whole cascade. The `--async-dma` flag is
kept in `n1_mha_chunked.py` but defaults off; the default path is verified
unregressed (54.3 ms, exact).

**The real bottleneck:** 54.3 ms for 8 chunks = **6.8 ms per 128-key chunk**,
moving only ~68 KB (36 KB QK + 32 KB V). That is ~1000× off what the NPU's DDR
bandwidth allows, so the cost is **per-chunk lock/DMA synchronisation across the
shim→mem→core cascade**, not data volume. C=2/4/8 times are 15.2/28.6/54.3 ms —
linear in chunk count with a large fixed per-chunk cost.

**Honest implication (correcting round 10's optimism):** wiring this attention
into the engine would NOT deliver FLM-class @1k prefill. At 6.8 ms/chunk, a
1024-token prefill would need query tiling (M≈64 max, limited by the M×HD×4
f32 O accumulator) → 16 query tiles × 8 chunks ≈ 0.9 s of attention per layer
before any GEMM, i.e. far past FLM. This attention is a **correctness proof**,
not a performance path.

**What FLM-class @1k prefill actually requires:** a redesigned batched attention
with far fewer synchronisation points — larger K/V tiles per step, K/V reuse
across query tiles (on-chip or minimal re-streaming), and a cascade that does not
round-trip locks per 128 keys. That is a multi-week kernel-design effort, not a
wiring task. Meanwhile the honest, verified position stands: **native wins decode
(78 vs 73.58) and wins prefill at 256 tokens (655-715 vs on-box 420-450); the
@1k prefill gap is real and architectural.**

   **member function** — pass `this` explicitly) and
   `_ZN3MHA21generate_mha_sequenceEP12npu_sequencejjjbi`.
2. **Clone `~/npu-build/mha/gen_attn_chunk.cpp`** (now in-tree under
   `npu-infer/tools/`? — it lives at `~/npu-build/mha/`, keep it) for that family:
   swap the include of the family's sequence header, the `from_pretrained` model
   dir, and link `-l<family>_npu` instead of `-lqwen3_npu`. Keep
   `-include climits`, `-I/usr/include/aiebu -laiebu`, and the
   `aiebu_assembler_get_elf(aiebu_assembler_buffer_type_blob_instr_transaction,
   ptr, nw*4, ...)` wrapper — that is the runtime's own ELF format.
3. **`MAX_L=32768`** (it sizes the runtime's KV BO: `MAX_L*NKV*HD*4`; the engine

4. **Generate `[0,1024)`**, drop it in `$NPU_XCLBIN_DIR/attn_mha_1024_nh16.elf`
