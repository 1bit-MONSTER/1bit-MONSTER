# BOTH MoE ELFs — the committed v1.0.x and the regenerated v0.9.46 — NaN on all-zero BOs

Addendum 160 concluded that v0.9.46 "generates the CORRECT whole-layer sequence" while v1.0.x NaNs,
and proposed regenerating from v0.9.46 as the path forward. **That conclusion came from *decoding* the
TXN, not from *running* it. I ran it.**

## Setup, and one thing that had to be fixed first

The v0.9.46 ELF initially failed outright:

```
MoERuntimeLayer: runlist FAILED: runlist failed execution (ERT_CMD_STATE_TIMEOUT)
```

Two mismatches, both found from `decode_txn`:

1. **region-B base** — the v0.9.46 ELF reads it at `0x1E000000` (503,316,480), the committed one at
   `0x1BC00000`. Sizing the BO for one and running the other puts every weight read out of bounds.
2. **xclbin** — v0.9.46 ships its own set (`~/.local/flm-v0946/xclbins/Qwen3.6-35B-A3B-NPU2/`), and its
   `layer.xclbin` is a different size and md5 from the v1.0.x one. With the v1.0.x xclbin the runlist
   times out; with the matching v0.9.46 xclbin **it executes.**

`MOE_REGION_B_BASE` and `MOE_WEIGHT_BO_BYTES` are now env-overridable in `runtime_layer_moe.cpp` so
either layout can be exercised without a rebuild. The v0.9.46 ELF's arg0 reads end at **533,293,056 B**
— 51,357,696 B past the v1.0.x-sized BO — which is what the timeout was.

## The result

With the matching pair, and with **every BO the harness controls zeroed**:

```
MOE_ZERO_WEIGHTS=1 MOE_ZERO_ACT=1 MOE_ZERO_NORMS=1 MOE_ZERO_ROUTER=1
MoERuntimeLayer: WEIGHT BO ZEROED
MoERuntimeLayer: ROUTER ZEROED
MoERuntimeLayer: ENTIRE NORMS BO ZEROED
MoERuntimeLayer: ACT ZEROED
logits: ALL NaN (of 248320)
```

**All five BOs zero, and the v0.9.46 ELF still outputs NaN.** The kv/state BO is memset to zero at
init, so *every* input to this ELF is zero.

## What this establishes

- **The NaN is not version-specific.** The committed v1.0.x ELF and the v0.9.46-regenerated ELF both
  produce NaN from all-zero inputs. Replacing one with the other cannot fix it.
- **"v0.9.46 generates the correct sequence" is a statement about the decoded TXN, not about a run.**
  The TXN may well be correctly generated — I am not disputing the decode — but a correctly generated
  program that outputs NaN when executed on zeros is not a usable path.
- **The remaining common factor is the driving, not the ELF.** Both ELFs are run through the same
  `MoERuntimeLayerEngine`: same BO sizing, same arg binding, same hw_context construction, same runlist
  submission. Since the inputs are eliminated and the two ELFs differ, **what they share is the thing
  still worth suspecting** — the harness/driver path, not the ELF contents.

## What is NOT established

- **Not** that the driver is at fault. That is where the evidence now points, but "both ELFs agree" is
  also consistent with both being generated by the same vendor flow with the same defect.
- **Not** that the weights or layout are irrelevant — only that they cannot be the *cause* of a NaN
  that appears when they are all zero.
- **Not** that a rebuilt ELF is useless. Only that swapping in the v0.9.46 one is not the fix, on
  measurement.

## The next thing to check, and it is cheap

Addendum 148 verified the **arg binding** by decoding it, and found it consistent. But it has never
been verified by **running** an ELF whose inputs are all zero and asking what a correct implementation
*would* produce. With every BO zero, a correct layer returns zeros. So the question is now narrow:

**which argument, or which BO size/alignment, makes this ELF return NaN from zeros?** The binding is
the first place to look, because it is the only thing two different ELFs share.
