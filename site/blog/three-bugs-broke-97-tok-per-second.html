NPU Debugging Postmortem

bong-water-water-bong · July 6, 2026 · 7 min read

Three bugs that broke 97 tok/s — debugging NPU inference

tl;dr: We claimed 97 tok/s. The speed was real. But the output was complete garbage — and nobody noticed, because every benchmark measured tokens per second, not correctness.

"What is 2+2?"

On July 3, I sat down to ask the engine a question. FLM answered: " 4." Correct. v12 — our engine, "97 tok/s, beats FLM" — produced complete garbage. The speed was real. The output never was.

Three bugs. All present since day one.

Bug #1: The LM head lies

🔴 LM head weight substitution
lm_head.weight gets dequantized, then discarded. Logits read from the embedding table instead. Qwen3-0.6B stores them separately — confirmed by Q4NX header.

Bug #2: The weight transpose

🔴 Weight-packing transpose
Dequant returns row-major [out_features, in_features]. GEMM needs [in_features, out_features]. Wrong stride scrambled every matrix — while producing finite, plausible-looking numbers.

Bug #3: The clipping that compounded

🔴 Activation quantization clipping
Hardcoded INT8 scale assumed [-5,5]. Measured: [-8.24, 7.01]. Clipped every layer, compounding across all 28.

All three fixed in all three copies of the logic. Output still incoherent. The fourth bug was in AMD's MLIR generator — missing AIE micro-tiling in the compiled xclbin kernels.

The fix

  1. xclbin output width matched to host buffer
  2. Valid chat template (not malformed test input)
  3. RMSNorm weight clip [-2,2]
  4. GEMM kernel verified bit-exact via hardware dump
  5. AIE micro-tiling corrected in MLIR generator

97 tok/s v12 now produces coherent output.

The lesson: Speed benchmarks lie. "2+2?" should always get "4." — if it doesn't, you don't have 97 tok/s. You have garbage at 97 tok/s.
