Two PCs, Two GPUs, Zero Cloud

HARNESS LAN LOCAL AI · August 19, 2026 · bong-water-water-bong

We took the "use your own iron" idea as far as it goes: two independent DeepSeek Harness agent instances on two PCs on one LAN — each with its own web GUI, a cross-PC message relay, and 1bit.MONSTER serving inference on both GPUs. No cloud LLM anywhere in the loop. This post is the record: the topology, the relay, the engine on both accelerators, the six real bugs we had to fix to get there, and the fully offline step that comes next.

Both machines run a dsh web harness bound to 127.0.0.1:3080 (the CLI deliberately refuses --host 0.0.0.0 for safety), exposed to the LAN through a tiny TCP forwarder plus the API's --trusted-host fence. Two harnesses, two GUIs, cross-reachable from either machine's browser.

The relay — two agents talking

dsh-relay (an HTTP mailbox on ryzen :9090) plus dsh-delegate turns the two harnesses into a two-node fleet: send a task, poll for the reply, done. 

# from either agent's shell
dsh-delegate ryzen "run the test suite and reply with the results"

Verified end-to-end over the LAN: compute 6*7 → "The answer is 42." — queued, delivered, drained, exit 0.

The engine — 1bit.MONSTER on both GPUs

Your own pure-C++ inference engine, built from source on each machine. Three OpenAI-compatible endpoints, one shared bearer token:

:8089 strixhaloRadeon 8060S (unified)Qwen3.6-35B-A3B Q8~166 tok/s

dsh-llm wraps all three: 

dsh-llm chat "explain quantum entanglement"         # 35B, strixhalo
dsh-llm chat -e ryzen "quick question"             # 8B, ryzen
dsh-llm vision photo.png "what is in this image?" # Qwen3-VL

What we had to fix to get there

Bringing up two machines surfaced six real engine bugs — all committed back to the engine:

  1. Chat-template detection — inferred from the filename "Instruct" heuristic, which missed models like Qwen3-0.6B; now reads the GGUF's own tokenizer.chat_template, and matches discovered models by normalized bidirectional prefix (Meta-Llama-3.1-8B-Instruct-Q4_K_M vs Meta Llama 3.1 8B Instruct).
  2. OOM guard — the generic-CPU fallback dequantizes the whole model to f32 in RAM (~4× size; 32 GB for the 8B), killing a 45 GB host even though the GPU path worked. UNIFIED_GPU_ONLY=1 strips CPU backends from the route.
  3. Sampler looping — the ggml-vulkan backend lacked the repeat-penalty sampler; instruct models echoed the prompt forever. Added llama_sampler_init_penalties.
  4. EOG leakage — <|eot_id|> leaked into responses; the end token and trailing whitespace are now stripped from output.
  5. Vision-encoder swap detection — compared only weight element counts (identical in both FFN orientations); now uses bias shapes as ground truth, unblocking the Qwen3-VL mmproj.
  6. VL server template — raw role: text mixed with ChatML markers produced degenerate output; ChatML mode now omits the role prefix.

All your own hardware — and next, none of the network

Everything above runs on the two machines in this house: both GPUs, both engine builds, your models, your LAN, one shared token. The fleet is boot-safe (user systemd + linger) and one command reports all of it: 

dsh-status

The offline step

Another agent is now building an ISO with its own custom kernel and drivers — a live-USB, fully-offline image so this entire stack (harness + engine + models) runs with zero network, zero cloud, zero assumptions. That's the natural end of this thread: home hardware today, self-contained USB stick next. Watch this space.
