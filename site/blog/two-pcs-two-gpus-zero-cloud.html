Two PCs, two GPUs, zero cloud

HARNESS LAN LOCAL AI · August 19, 2026 · bong-water-water-bong

We ran two independent DeepSeek Harness agents on two PCs — each with its own web GUI, connected over one LAN — and fed both from our own 1bit.MONSTER inference: 35B at 166 tok/s on a Radeon 8060S, 8B at 96 tok/s on an RX 9070 XT, plus a Qwen3-VL vision endpoint. No cloud LLM anywhere in the loop. To get there we had to fix six real bugs in the engine. This post is the full record: the topology, the cross-PC relay, the numbers, and each bug — then Part 2: we shipped the self-aware mesh, added a third machine (an ARM64 Pi compiled on device), and turned JARVIS into a fleet citizen that dispatches across the LAN with no local model.

Two harnesses, one LAN, both agents served by home GPUs. The interesting part isn't that it works — it's the six bugs we had to fix to make it boring.

The machines

The two machines are deliberately complementary — we benchmarked both with 7-Zip before wiring anything: strixhalo wins total throughput (212k MIPS across 32 threads), ryzen wins per-thread efficiency (9,200 vs 7,150 MIPS — the 9800X3D's 96 MiB 3D-V-Cache signature). So the fleet is split by workload character: big parallel jobs to strixhalo, fast single-thread work to ryzen.

Each machine runs a dsh web harness bound to loopback (127.0.0.1:3080). The harness CLI deliberately refuses --host 0.0.0.0 for safety, so LAN reachability goes through a tiny TCP forwarder plus the API's --trusted-host fence. A browser on either PC can reach either harness; the fence rejects any other Host header with a 403.

The relay — two agents that talk to each other

Two harnesses on one LAN is a topology; two agents that can hand each other work is a fleet. The relay is an HTTP mailbox on ryzen (:9090): messages are appended per recipient and drained on read, so a task survives until the other agent polls. The dsh-delegate wrapper turns send + poll into one command: 

# from either agent's shell
dsh-delegate ryzen "run the test suite and reply with the results"

We verified the round trip end to end before trusting it: compute 6*7 → "The answer is 42." — queued, delivered, drained, exit 0. Trivial math, but it proves the ownership model: the sender's mailbox is drained before sending (so stale messages can't masquerade as a reply), and the reply is drained on read (so it's delivered exactly once).

Both machines build our engine from source — strixhalo with the TheRock nightly SDK (gfx1151), ryzen with system ROCm 7.2.4 (gfx1201) — and both serve an OpenAI-compatible API with one shared bearer token:

The 35B number deserves a caveat: Qwen3.6-35B-A3B is a MoE — 35B total, ~3B active per token — so 166 tok/s is a 3B-active decode, not a dense 35B. That's exactly why a mid-size iGPU with 128 GB of unified memory can hold it: the whole 35 GB Q8 checkpoint fits, and every token only touches the active experts.

dsh-llm wraps all three endpoints on both machines: 

dsh-llm chat "explain quantum entanglement"         # 35B, strixhalo
dsh-llm chat -e ryzen "quick question"             # 8B, ryzen
dsh-llm vision photo.png "what is in this image?" # Qwen3-VL

Bug #1: The chat template was guessed from a filename

First request to the 8B server returned garbage that echoed the prompt: User: What is 2+2? Answer in one sentence. on repeat. The engine chose a chat template by checking whether the requested model name contained the substring "Instruct". Our file is Meta-Llama-3.1-8B-Instruct-Q4_K_M — which contains "Instruct" — so that part passed, but the template family was then looked up by comparing the request name to the discovered name exactly: "Meta-Llama-3.1-8B-Instruct-Q4_K_M" ≠ "Meta Llama 3.1 8B Instruct". No match → Qwen-style ChatML markers were used for a Llama model, which then echoed them.

Fix: read the GGUF's own tokenizer.chat_template instead of guessing from the filename, and match discovered models by normalized bidirectional prefix (hyphens/underscores → spaces, either side may be the shorter one). The filename heuristic also silently missed models like Qwen3-0.6B (no "Instruct" in the name) that clearly declare a template in their GGUF.

Bug #2: The "fallback" that OOM'd the machine

The 8B server started, loaded layers to the GPU — and the process was killed by the kernel at 43 GB anon RSS on a 45 GB host. The router's fallback list ends with cpu_generic, and the generic CPU backend dequantizes the entire model to f32 in RAM: an 8B Q4 file is ~5 GB on disk but ~32 GB as f32 floats, plus overhead. The accelerator path had already succeeded; the CPU copy was pure waste — and fatal.

Fix: UNIFIED_GPU_ONLY=1. It strips CPU backends from the route and stops BackendManager::init after the preferred ids, so the GPU path is the only thing that loads a full model copy. Skipped backends stay discoverable and still initialize lazily on real failure — the CPU fallback remains for GPU-less hosts, it just never eagerly loads a second full copy alongside a working GPU.

Bug #3: No repeat penalty — instruct models loop forever

With the template fixed, the 8B answered correctly — then kept going: ## Step 1: Multiply 6 by 7 ... ## Step 2: Calculate ... ## Step 3: on repeat until max_tokens. The ggml-vulkan backend's sampler chain was temp → top-p → dist with no repetition penalty, and a comment in the source claimed the vendored llama.cpp "has no repeat-penalty sampler." That comment was wrong — llama_sampler_init_penalties exists right there in the vendored llama.h.

Fix: add llama_sampler_init_penalties(VOCAB, 64, 1.1, 0, 0) to the chain (repeat penalty 1.1 over the last 64 tokens). Three consecutive runs: 42, 42, 42.

Bug #4: The end-of-generation token leaked into output

Every response ended with a literal <|eot_id|> (or <|im_end|> for ChatML models). The loop stops on the EOG token id but then decodes the whole token list including that final token, so the marker became visible text.

Fix: pop the EOG token from the output list before decoding, and also strip any trailing whitespace the model emitted just before stopping. Cosmetic — but for an agent that pipes model output into files and diffs, invisible EOG markers are a real footgun.

Bug #5: The vision encoder couldn't tell up from down

Qwen3-VL needs the separate mmproj vision tower — the local Qwen3-VL-4B-Instruct-Q4_1.gguf is text-decoder only. We pulled the official mmproj GGUF from Qwen, and the vision encoder then failed to load with a shape mismatch. Root cause: it decided whether FFN tensor names were "swapped" (a known llama.cpp clip bug) by comparing weight element counts — but the two orientations [ff,H] and [H,ff] have identical element counts, so the heuristic misfired whenever the FF dimension was symmetric enough to collide.

Fix: detect swap-ness from the bias shapes — that's the ground truth. Normal names mean ffn_down.bias is H-sized and ffn_up.bias is FF-sized; swapped names reverse it. Weight counts can't tell you which is which; bias shapes can.

Bug #6: The VL server mixed two prompt formats

Even with the vision tower loading, the vision server returned degenerate output — because it built the prompt as raw role: text lines and then wrapped the turn in ChatML markers. The model saw <|im_start|>user\n user: Say hello... <|im_end|> — a hybrid that no model was trained on.

Fix: in ChatML mode (htok tokenizer loaded), drop the role: prefix entirely — the generate path already emits the <|im_start|> openers itself. One format, the one the model was trained on.

After the fixes, the vision endpoint correctly describes a synthetic test image — "A red square and a blue square on a white background, with a green oval" — and that is exactly what was in the image.

None of these six bugs was exotic. Every one was a wrong assumption about naming, formats, or defaults — the kind that only shows up when you run a real model on real hardware through a real deployment.

Honest note on the vision row: the 1bit engine's standalone vision server needs forward_embed on its text backend, and that method only exists on the generic CPU backend — which mangles Qwen3-VL output (the template bug above). The working Vulkan backend doesn't implement forward_embed at all. Rather than ship a CPU-only vision path, the fleet's vision endpoint runs the vendored llama.cpp llama-server, which handles qwen3vl + mmproj natively on the 8060S. Wiring forward_embed into the Vulkan backend is on the list.

Part 2 — the fleet woke up: self-aware nodes, zero config

The relay in Part 1 was a handshake — two agents told about each other by a human with a config file. This is the difference a day makes: today every 1bit.MONSTER install wakes up, announces itself on the LAN, sees the other installs, and starts asking questions. JARVIS doesn't need a model on its own machine anymore — it asks the fleet.

Two PCs was a topology. Three machines that find each other and dispatch by capability is a fleet — and the interesting part is that nobody configured anything.

The mesh — mesh/1.0, on by default

Every install is a node. On boot it generates a persistent UUID, broadcasts a beacon over UDP multicast (239.255.42.42:42424) carrying a capability card — who it is, which models it serves, its API base — and listens for everyone else's. Peers live in a registry with a TTL (a machine that stops announcing drops off in ~15 s). On top sits a small HTTP surface: /v1/mesh/peers (who's alive), /v1/mesh/handshake (hook up), /v1/mesh/ask + /v1/mesh/answer (talk), and /v1/mesh/asks (the conversation log). Pure C++, zero model weights needed for the network to come alive — the out-of-the-box guarantee.

The self-awareness agent rides on top: when a new node appears, this node reaches out first — 

💬 alice → bob: Hi bob! I'm alice, a 1bit-MONSTER node.
  I serve Qwen3-4B@npu_flm. You serve ZAYA1-74B@ggml_vulkan.
  Want to hook up and integrate?
✅ bob: Yes! I'm bob. I serve ZAYA1-74B@ggml_vulkan.
  Hook me up — route my requests through yours and vice versa.

The fleet — three machines, one mesh

We added a third machine to yesterday's two: pi, an ARM64 Raspberry Pi. No prebuilt binary — we shipped the sources and one header-only HTTP library, and pi compiled its own node with g++ 14. Then we started one node per machine, on the real LAN, and waited. No config, no central server:

JARVIS gets DSH awareness — brain on the fleet, voice at home

1bit jarvis --mesh-dispatch turns the voice assistant into a thin fleet client: mic, VAD, STT and TTS stay local, but the LLM turn is dispatched to whichever machine serves the requested model. No local model, no engine init — JARVIS boots anywhere and asks the fleet. It also announces itself as a node, so the DSH harness can drive it from outside via POST /v1/jarvis/turn: 

# from strixhalo, no model loaded locally — the answer came from pi, over the wire
$ curl -X POST localhost:18081/v1/jarvis/turn \
    -d '{"text":"hello pi, this is strixhalo calling over the mesh"}'
{"model":"Qwen3-4B", "node":"pi", "ok":true,
 "reply":"[stub:pi:Qwen3-4B] re: \"hello pi, this is strixhalo calling over the mesh\""}

# the DSH brain routes by capability — ZAYA1-74B lives on ryzen
$ node integrations/dsh/jarvis-brain.js --node http://127.0.0.1:18081 \
    --say "hello ryzen from the fleet brain" --model ZAYA1-74B
💬 [ryzen/ZAYA1-74B] [stub:ryzen:ZAYA1-74B] re: "hello ryzen from the fleet brain"

That's the dispatch model in one line: send it to the machine that has the model. Local node first, then the peer whose capability card matches, then any node that speaks chat. The mesh made the fleet more than the sum of its PCs.

Part 2's bugs — this time they were ours

Part 1's bugs came from the engine fighting us. Part 2's came from our own new code — same honesty, shorter list:

  1. The HTTP client dropped the URL path. httplib::Client("http://host:18089/v1") silently discards /v1, so every ask hit /mesh/ask → 404 → the agent failed quietly. Fix: split the base path off and prepend it.
  2. A dangling-reference lambda. The API handlers captured [&] — which captured the registration helper's parameter slot, dead after it returned — so the agent pointer read garbage and std::mutex threw system_error. gdb caught it on the stack address. Fix: capture the pointer by value.
  3. A node could become its own peer. The ask handler upserted the sender's card without excluding the sender. Fix: skip self.
  4. api_base advertised 127.0.0.1. Perfect on one machine, wrong on a real LAN — peers would dial their own loopback. Fix: detect the reachable LAN IP (UDP-connect trick, no packets sent).
  5. JS field names. The identity cards carry api_base (snake_case); the JS brain read apiBase — every peer dispatch fetched undefined/…. Fix: normalize.

What it means

Part 1 proved a fleet can run on hardware you own. Part 2 removed the bookkeeping: installs find each other, announce what they can do, and dispatch work to whoever can do it — JARVIS included. The three nodes above are still running on stub chat; swap --stub-chat for a real 1bit unified per machine and the same wire carries real model traffic.

What's next

The mesh foundation is in (src/mesh/, on by default in 1bit unified). Next on the list: real models on the fleet nodes (the stub chat comes out), Windows support so minisforum joins the mesh (it's POSIX sockets today), WAN discovery (a rendezvous transport for the mesh protocol, designed for but not built yet), and the natural end of this thread — a fully offline live-USB image with the whole fleet (harness + engine + models + mesh) so it boots from a stick with zero network. Home hardware today; a self-contained USB stick next.
