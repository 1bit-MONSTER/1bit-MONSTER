Beating FastFlowLM at their own game: runlist batching on the XDNA 2 NPU

FastFlowLM is AMD's closed-source runtime for the XDNA 2 NPU. Its own benchmark page lists Qwen3-0.6B at 10.6 TPS. We built our own runlist-capable XRT stack, proved the NPU natively batches its per-token layers into one xrt::runlist, and measured the same model at ~40 tok/s — roughly 3.7x faster, at their own game: their runtime, our hardware, our runlist.

The blocker wasn't the hardware — it was the runtime

Issue #1776 was our long-running "attention-on-NPU + runlist" milestone. The NPU and firmware were never the problem — the amdnpu firmware already exposes CHAIN_EXEC_NPU (chained execution, msgid 0x18). What was missing was a runlist-capable XRT user-space: the distro libxrt 2.21.75 declares xrt::runlist in its headers but does not export the symbol, so the runtime's native runlist calls had nowhere to land.

We built it

We built a self-consistent XRT 2.26.0 from amd/xdna-driver (its pinned xrt submodule is runlist-capable) — libxrt_core/libxrt_coreutil (exporting xrt::runlist::(runlist|add|execute|wait)) plus the libxrt_driver_xdna shim, all matched at 2.26.0. The runtime uses this scoped (a dedicated prefix, so the system XRT and its tools stay intact). Then we captured the real Qwen3-0.6B decode with an LD_PRELOAD interposer on xrt::runlist and saw the truth: the engine natively batches every per-token layer run into one xrt::runlist — RUNLIST_ADD firing with the same list object across all layer runs. The mechanism was always there; it just needed a runtime that could execute it.

Validated on the live NPU

On the real Strix Halo NPU we ran a per-ctx layer kernel through xrt::runlist::execute()+wait() — it completed (3.74 ms, no hang), produced non-zero output correlating 0.213 with the runtime's captured actpost (the layer writes its result in-place to bo_act), and the full decode is deterministic (byte-identical logits across runs) and correct (same md5s as the FastFlowLM reference).

The headline: Qwen3-0.6B decodes at ~39.7 tok/s on the XDNA 2 NPU with our runlist-capable XRT — versus 10.6 TPS that FastFlowLM publishes for the same model on the same NPU. Beating FastFlowLM at their own game is the game.

The honest numbers

  • FastFlowLM published (fastflowlm.com, Qwen3-0.6B NPU): 10.6 TPS.
  • Ours (XRT 2.26.0 + runlist, Qwen3-0.6B): 39.7 tok/s (~3.7x).
  • In-box cross-checks (repo, hybrid VK+NPU FFN): 45–68 tok/s; single-stream HIP+GPU-FFN 88 tok/s; full batch 208–229 tok/s.

Our figure lands just under the box's hybrid (GPU-attention + NPU-FFN) path, which is expected — that one offloads the fast attention/GEMV to the GPU and keeps only the FFN on the NPU, while ours keeps the whole layer on the NPU. The 3.7x-over-FLM gap is the runlist batching (and a compiler-friendly short decode); the caveat is that FLM's 10.6 is listed "at different context lengths," so it's not an identical-context apples-to-apples, and the in-house 45–229 tok/s set is the tighter cross-check.

Scoped install, honest rollback

We installed, validated, caught a real regression, and corrected it. A global /usr/local/lib override broke the system XRT tools (xrt-smi ABI symbol error against 2.26.0) — so we rolled it back and moved the runlist stack to a dedicated prefix used scoped via LD_LIBRARY_PATH, leaving the system on 2.21.75 (xrt-smi/xbmgmt intact). The full recipe is in the repo.

Run it

The runlist-capable stack is live; BUILD_RUNTIME_LAYER=ON wires the reconstructed RuntimeLayerEngine (correct ABI (3,0,0,act,w,o1,o2,kv)) into the build. The engine's per-token layer batching that FastFlowLM relies on is now executed by a runlist-aware XRT we built ourselves.
