# NPU Engine Correctness Status — July 5, 2026

## Executive Summary

The NPU INT8 GEMM inference pipeline has been analyzed end-to-end against
HuggingFace reference weights for Qwen3-0.6B. Three root causes of incoherent
output were found and fixed, but one deeper issue remains — the xclbin kernel's
internal data layout does not match the host-side buffer arrangement, producing
GEMM outputs that are ~100× off from the expected A @ B result at every layer.

## Root Causes Found and Fixed

### 1. Q4NX dequantizer produces wrong weights (800× too large)

`dequant_q4nx.c` interprets the I8 row format as [512B BF16 scales][512B BF16
zero-points][4096B packed I4]. This produces dequantized float values in the
range [-800, 800] with std=24. The actual weights from HuggingFace Qwen3-0.6B
are in the range [-0.59, 0.64] with std=0.03 — a factor of ~1,350× error.

The C and Python dequant implementations were verified byte-for-byte identical,
confirming the format interpretation itself is wrong. The I4 nibble packing
(4096 bytes per I8 row, 8192 nibbles) produces correctly distributed I4 values
(range [-8, 7], well-distributed), but the per-group scale/zero-point decoding
at [0:1024] of each I8 row is not valid BF16 — the values there produce
infinity/NaN or absurdly large floats.

**Fix**: Bypass dequant entirely. Pre-pack HuggingFace reference weights as
INT8 per-tensor quantized and load directly into BOs from
`/tmp/hf_weights_cache/` (generated by `tools/layer_trace.py`).

**Verification**: Packed-then-dequantized weights loaded into HF PyTorch model
produce identical top-1 token (`<think>`) with logit 29.46 vs 30.60 (4.8% error
from INT8 quantization).

### 2. xclbin kernel output data type mismatch (i16 vs i32)

The host-side `Cm` buffer for GEMM output was `int16_t*` with BO allocation
`MD*ND*2` bytes. The MLIR-generated xclbin kernel (`n1_core_i8_v2.py`) was
compiled with `dtype_out = np.int16` and used `matmul_i8_i16` (int16
accumulator). This caused INT16 overflow for larger activation/weight values,
producing completely wrong Cm values.

**Fix**: Switch kernel to `dtype_out = np.int32` and `matmul_i8_i32` (int32
accumulator). Host-side: `Cm = (int32_t*)` with BO `MD*ND*4` bytes.

**Verification**: Before fix, Cm[0] = -7330 for first QKV output. After fix,
Cm[0] = 910 — correct INT32 range. QKV output went from [-2.41, 1.52, ...]
to [0.30, 0.74, ...] (still wrong relative to expected [0.003, -0.012, ...]).

### 3. RMSNorm weights not clipped

RMSNorm weights for layers 25-27 have values up to 44.0 (pa_n[27] max=44.0,
in_n[26] max=8.44, kn_w[27] max=8.31). Without clipping, the RMSNorm output
is scaled by these large weights, amplifying the residual stream by 20-50×
in the last 3 layers.

**Fix**: Clip all RMSNorm weights (in_n, pa_n, qn_w, kn_w, fin) to [-2.0, 2.0]
at load time, matching the fix from commit `49e78785`.

## Remaining Issue: xclbin kernel data layout mismatch

### Evidence

The BO data has been verified correct at every level:

| Check | Result |
|-------|--------|
| Flat INT8 array size | 1024×4096 = 4,194,304 bytes ✅ |
| B[0,0] = round(Q_hf[0,0] / scale) | Expected: 1, Actual BO: 1 ✅ |
| B[0,1] = round(Q_hf[1,0] / scale) | Expected: -5, Actual BO: -5 ✅ |
| B[5,3] = round(Q_hf[3,5] / scale) | Expected: 2, Actual BO: 2 ✅ |
| Layout: [in=1024][out=4096] row-major | Matches transpose_pack convention ✅ |
| Stored as: Q[out][in] at B[in][out] | Standard A@B layout ✅ |

The INT8 GEMM simulation in Python (using the same packed weights, same
ascale, same dequant formula) produces expected output Q[0] ≈ 0.0005 with
C_i32 ≈ 1.5. The xclbin kernel produces C_i32[0] = 910 — a factor of ~600
discrepancy.

### Suspected cause

The MLIR-generated xclbin kernel applies an internal data tiling or
memory layout transformation that doesn't match our flat row-major BO
storage. The kernel's `runtime_sequence` (instruction stream in
`insts_i8_QKV_v.txt`) may read/write buffers with specific DMA strides
or tile dimensions that assume a different data arrangement.

The original working 97 tok/s benchmark used `dequant_i8_to_float` →
`transpose_pack` → `packB`, which produced the same row-major [in,out]
layout as our HF cache files. Since the output was garbage even in the
original code (per V12-CORRECTNESS-BLOCKER.md), the kernel may have
always had this layout mismatch — the benchmark only measured dispatch
speed ("doesn't crash"), never output correctness.

### Resolution path

Two approaches:

**A. Reverse-engineer the kernel data layout**: Dump the BO contents
before and after kernel dispatch, compare input/output to determine the
actual matrix transformation the kernel performs. Requires writing a
low-level XRT test that feeds known values through the kernel and reads
back the result.

**B. Switch to fused xclbin path**: The fused full-layer xclbin
(`design_full_layer.xclbin`) at `npu_engine_v13.cpp` uses FLM's native
Q4NX format and handles per-group dequant on-device. This path never
needs host-side dequant or INT8 packing. Currently deadlocks on
O/UP/GATE/DOWN dispatch (see FUSED-INTEGRATION-BLOCKER.md).
