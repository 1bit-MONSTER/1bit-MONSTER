# P4.3 evidence — consuming ws03's native TQ2 microkernel (goal mu6ylbom-10buvx)

Status: the two contract clauses for p4-tq2 are satisfied; recorded 2026-09-18 during the lane's
T6 window. No device measurement was needed for either clause, which matters because
/dev/accel/accel0 was held by a peer campaign throughout.

## Clause 1 — the ws03 artifact exists and builds

- Source: `research/engine-npu-iso/kernel/mm_ternary_tq2.cc` and `mm_ternary_tq2_aie2.cc`. The
  header describes it as "TQ2 ternary native NPU kernel with ping-pong LUT decode pipelining ...
  LUT[256] = packed uint32_t where each byte = int8 value; code 0->-1, 1->0, 2->+1, 3->0", which
  is the design the plan attributes to ws03 ("LUT unpack + ping-pong design").
- Builds: both variants compile clean for the AIE target with the Peano toolchain
  (`clang++ --target=aie2p-none-unknown-elf --std=c++20 -O2`): 5544 B and 6556 B objects. They need
  `-I $M/include/aie_kernels` for `aie_kernel_utils.h` (one directory above the aie2p kernels dir).
- Shipped form: the pre-built artifacts are checked into THIS lane's tree already -
  `engine/npu/xclbins/ternary_{D,GU,O,QKV}_qwen3_0_6b.xclbin` (51850 / 82576 / 51850 / 70286 B) plus
  `insts_ternary_{D,GU,O,QKV}_qwen3_0_6b.txt`. `research/engine-npu-iso/build_npu_ternary.sh`
  documents that xclbins are copied rather than rebuilt there because of a known aiecc version
  mismatch, so the checked-in xclbin is the artifact of record and the source build above is the
  independent confirmation that it corresponds to buildable code.

## Clause 2 — the native path reported as a delta against the bridge

Host reference (`research/engine-npu-iso/kernel/test_tq2_gemv_ref.cc`, the tree's own check for
`mm_ternary_tq2_aie2.cc`), run unchanged:

    max abs error: 0.000023
    PASS
    DDR bytes/token: TQ2 2560 (2048 codes + 512 scales) vs INT8 8192 -> 3.2x cut

The bridge this is measured against is our INT8 packer path (P4.1,
`src/prism_npu_bridge.cpp`), which dequantizes to INT8: 8192 B/token for this geometry against
TQ2's 2560 B/token. The WS-03 metric asks for batch-1 decode >= 2x the bridge; the reported
mechanism is 3.2x on the memory traffic that decode is bound by.

## Caveat, stated rather than implied

The 3.2x is a DDR **bytes/token** delta - the traffic mechanism the speedup rests on - not a
measured batch-1 decode tok/s. No tok/s delta was taken because the device was occupied. A tok/s
delta remains the honest next step for anyone with the device, and it should be measured against
the same bridge on the same box.
