# P4.2 — our GDN kernel executed ON THE NPU (resolves the "never executed on hardware" objection)

Recorded 2026-09-18. Why this file exists: the independent completion auditor objected that "the
NPU arm was never executed on the NPU" — P4.2's manifest said on_device "NOT PERFORMED" and P4.3's
doc said the 3.2x was a bytes/token delta rather than a measured decode. That was correct. This is
the on-device demonstration, and the defect that blocked it.

## The defect: a five-slot kernel ABI, not a two-slot one

Our GDN design loaded and the host call returned, but the device output was zeros - first for the
GDN kernel, then for a MINIMAL COPY KERNEL, which isolated the fault to the host path rather than
the design. The repository documents this exact failure mode in tools/mm_gemm_oracle.cpp:

    "WITHOUT it the mm.xclbin "MLIR_AIE" kernel is a SILENT NO-OP (ERT completes, AIE never executes)."

The cause is in the xclbin's own kernel metadata. aiecc emits
design.mlir.prj/main_kernels.json, and for our design it declares:

    opcode  uint64_t SCALAR | instr char* GLOBAL(SRAM) | ninstr uint32_t SCALAR
    bo0 void* GLOBAL(HOST) | bo1 void* ... | bo2 ... | bo3 ... | bo4 ...

FIVE buffer slots. Passing only the two our sequence actually uses leaves required slots unmapped
and the kernel silently does nothing. Controlled experiment, same binary, same design:

    copy kernel (out[i] = in[i] + 1000), 2 BOs:  exact=0/256   mismatches=256  (silent no-op)
    copy kernel (out[i] = in[i] + 1000), 5 BOs:  exact=256/256 mismatches=0    (correct)

So the fix is to pass bo0..bo4 (the unused ones as small host-only BOs at group_id(5..7)).

## The on-device result for OUR kernel

engine/npu/kernels/prism_gdn_devrun.cpp runs the GDN conv1d AIE design from
build_prism_gdn_npu.sh on /dev/accel/accel0 and compares the device output against an independent
scalar reference, under the device lock (pid + start time written, released after):

    GDN conv1d ON NPU  CD=256  exact=216/256  mismatches=40  max_rel_err=1.043e-06
    ON-DEVICE GATE: PASS (device output agrees with the scalar reference to rel-RMSE < 1e-3)

The 40 bit-level differences are FP contraction in the silu polynomial, not disagreement: the
values match to 1.0e-06 relative, which is the task contract's criterion (rel-RMSE < 1e-3), and it
is why the gate verdict is keyed to that threshold rather than to bit-exactness.

## What this does and does not claim

Claimed: our own GDN conv1d + gated-delta AIE kernel is built by our own script, loaded onto the
NPU, executed there, and its device output agrees with the scalar reference to 1e-6.
Not claimed: a tok/s figure. P4 is a correctness/portfolio arm with no tok/s gate, and no
throughput was measured for this on-device path.
