## What this means for our targets

1. **The fork is not the ceiling.** Its 1-bit run moves 3.79 GB/token at 28.8 tok/s = **109 GB/s** —
   exactly the *CPU*-triad bandwidth on this box, while the device lane measures **201–219 GB/s**
   (`tests/hip_bw_probe.cu`). So the reference implementation leaves ~1.85× on the table, and our
   ≥42 tok/s plan target for the 1-bit model is a real, reachable goal rather than a stretch.
   It also explains the old `benchmarks/bonsai/RESULTS.md` 27B Q1_0 entry (3.6 GB @ 30 tok/s).
2. **The folded ternary path is the interesting one.** 4.4 tok/s on PTQ1_0 (folded, 5.95 GB) is
   ~26 GB/s — a per-op fallback, not a fused path. Whatever Hadamard placement the fork uses on
   Vulkan is worth reading before we design the fused `fwht→GEMV` (P3.1/P3.3): if the fork rotates
   per operator, our shared-slab rotation should be a large multiple.
3. **pp differs by 28× between the two models** (331 vs 11.8 t/s) with similar geometry — consistent
   with the folded path going through a slow generic dequant, not with geometry.

## Golden capture (the correctness oracle)

Deterministic settings used: `--temp 0 --top-k 1 -s 20260918 -c 4096 -n 24` (Q1_0) / `-n 8`
(PTQ1_0), prompt `The capital of France is`, single-turn, chat template from the GGUF.

```
Q1_0     : [Start thinking] Here's a thinking process: 1. **Analyze User Input:** The user says "The capital of France
PTQ1_0   : [Start thinking] User asks: "The capital of France
```

These prefixes (and their token ids, to be captured with `--logits`/`-n` extensions when our engine
can emit token ids) are the acceptance gate for P2: per-layer corr first, then identical greedy
tokens.
