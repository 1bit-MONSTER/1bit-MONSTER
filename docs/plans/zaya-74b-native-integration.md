# Implementation Plan: Native ZAYA1-74B integration into the C++ engine

> Generated by the planni workflow (scout + planner), 2026-08-05.

## Goal
Wire the 74B Zaya GGUF → OneBP → native HIP engine so `backend_hip.cpp` loads quantized Zaya models through the existing CCA attention + MoE kernels, reusing `ZayaState`/`LayerW` structs and the `generate()` path unchanged.

## Plan

### 1. Create `zaya_init_onebp()` in `zaya_engine.cpp`
Add a new function after `zaya_init()` that:
- Opens a `.1bp` file via `OnebpModel::load()`
- Validates dimensions against `eng` config (same embed-size gate as `zaya_init`)
- Allocates all GPU buffers identically to `zaya_init()` (factor into a reusable `zaya_alloc_buffers(ZayaState*)` helper called by both init paths)
- Loads weights via the tensor name mapping below, using `OnebpModel::get_tensor_f32()` for ndim=1/2, `get_tensor_f32_expert()` for ndim=3 MoE stacks
- Uploads to GPU via `upf16`/`upf32` (already defined)
- Returns `ZayaState*`

### 2. Factor GPU buffer allocation into a shared helper
Extract the ~80 lines of GPU `hipMalloc` for buffers (`d_hs`, `d_ao`, `d_tmp`, `d_fnw`, `d_lm_out`, `d_lm_vocab`, `d_embed`, `d_ibias`, `d_iscale`, `d_token_id`, `d_conv`, `d_phs`, `d_vrec`, `d_qout`, `d_kout`, `d_vout`, `d_skip_flag`, `d_prev_rs`, `d_expert_idx`, `d_expert_wt`, `d_sorted_ids`, `d_expert_counts`, `d_expert_offsets`, `d_argmax_idx`, `d_argmax_val`, KV cache, `d_partials`) into a static function `zaya_alloc_buffers(ZayaState* s)` called by both `zaya_init()` and `zaya_init_onebp()`.

### 3. Modify `backend_hip.cpp::init()` to detect OneBP/Q4NX format
Replace the hard `.bin` gate with:
1. Try `.1bp` file in `weights_dir` (scan directory, same pattern as `backend_laguna.cpp`)
2. If found → call `zaya_init_onebp(wd.c_str(), &zcfg)` instead of `zaya_init()`
3. If no `.1bp`, try legacy `.bin` check → `zaya_init()` (existing path)
4. If neither → return false

### 5. Handle 3D MoE expert packing
`ffn_gate_up_exps.weight` ndim=3 `[NE, 2*n_ff, H]`, tiled per-expert. `zaya_engine` expects `gu` as one contiguous fp16 buffer `[NE * 2 * n_ff * H]` with gate/up interleaved. Load each expert via `get_tensor_f32_expert()`, concatenate, then `upf16`. Same for `ffn_down_exps` `[NE, H, n_ff]` → `dn` `[NE * H * n_ff]`.

### 6. Handle 74B-specific dimension quirks
- `attn_output.weight` shape `[QD/2, H]` (half-dim CCA output). Kernel expects `wo` `[H, QD]`. Verify-or-transpose on load.
- `zaya_router_mlp4.weight`: GGUF stores `[NE+1, rtr_h]` = `[9, 256]` for 74B. Engine expects `[256, 256]`. Pad with zeros to square (pattern from `tests/zaya_gpu_decode.cpp`).
- `ffn_gate.weight`: GGUF stores `[H, rtr_h]`, zaya expects transposed `[rtr_h, H]`. Transpose on load.
- KV cache: 80 layers × 4096 seq × 8 NKV × 128 HD × 2 = ~670 MB fp16. `ALLOC_OR_FAIL` handles OOM.

## Risks
1. **OneBP tensor name conventions**: `gguf_to_onebp.cpp` preserves GGUF names verbatim. If 74B GGUF uses HF-style `model.layers.N.*` instead of `blk.N.*`, mapping misses. Mitigation: fallback aliases (pattern from `zaya_gpu_decode.cpp`'s `add_alias()`).
2. **zaya_router_mlp4 square-pad**: 74B has 8 experts (9 slots w/ skip token), so `mlp4` is `[9, 256]` not `[256, 256]`. Pad-to-square works but untested on 74B shapes. Padded invalid expert slots get zero logit (correct).
3. **MoE kernel shared-memory limits**: `zaya_router_moe.hip`, `zaya_moe_batch_union.hip` use compile-time smem. Batch path may fail for non-8B. But `generate()` uses single-token path (`zaya_forward_greedy`) via dynamic kernels (`zaya_gpu_router.hip`, `zaya_moe_tiled_gemv.hip`) — main path safe.
4. **VRAM for 74B embedding**: `vocab * H * 2` = 262K × 8192 × 2 ≈ 4.3 GB just for embedding table. `ALLOC_OR_FAIL` handles OOM.
5. **`input_hidden_states_scale/bias`**: 74B GGUF may not have these — should be optional (default scale=1.0, bias=0.0). Pattern in `zaya_gpu_decode.cpp`.
